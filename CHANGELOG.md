# Changelog

All notable changes to fractrade-hl-simple will be documented in this file.

## [Unreleased]

### Bug Fixes

Orders and other signed actions:

- **An order could be sent twice.** Orders, modifies, transfers and margin changes were retried after network errors and timeouts, even when the exchange had already executed them. They are now retried only when the request provably did not reach the exchange (rate limit, connect timeout). Every single order (market, limit, close, stop loss, take profit, spot, maker attempts) carries a client order id; if its response is lost or does not contain the order's status, the library looks the order up by that id and returns what the exchange reports, waiting until the fills of a filled or partly filled order are visible. If the outcome cannot be settled, `OrderOutcomeUnknownException` (new) is raised with the `cloid`. Transfers, margin changes and `bulk_order()` raise `ActionOutcomeUnknownException` (new) instead; a bulk order's orders carry the client order ids passed with them (see New Features). A response body that is not JSON counts as unknown, not as a failure.
- **Server errors (HTTP 5xx) were not retried on reads.** The SDK raises its own `ServerError`, which the retry logic did not catch. Reads, cancels and leverage changes now retry it.
- **Requests had no timeout**, so a stalled connection blocked forever. New `request_timeout` parameter, 10 seconds by default.
- **Two actions from the same key in the same millisecond collided.** The SDK uses the current millisecond as nonce. Signed actions are now serialized per signing key across all clients in the process, each with its own millisecond (after a clock change the wait is capped at one second).
- **Cancel results were ignored**, so a cancel the exchange never confirmed looked successful. `cancel_all_orders()` and `spot_cancel_all_orders()` raise `OrderException` naming every order that was not canceled; orders that already filled or were canceled count as done. `cancel_order()` and `spot_cancel_order()` returned `True` for an order that had already filled; they now return `False`.
- **`update_stop_loss()` / `update_take_profit()` could leave a position unprotected or doubly protected.** After any failed modify, even one whose response was only lost, they canceled the old order before placing a new one. They now place the new order first, sized to the live position, then cancel the old one, one replacement at a time per signing key. If the old one cannot be canceled, or the new one does not cover the whole position by then (the position grew, or it executed at once) or that cannot be checked, the old one stays and `ProtectionReplacementIncompleteException` (new) reports both. Every other signed action of the same key in the process (orders, cancels, closes) waits while a replacement runs; under rate limiting that wait includes the replacement's retries. Modify is no longer used for them: the exchange rejects modifying trigger orders.
- **`bulk_order()` returned any answer as a result**, also one without a status per order. It now raises `OrderRejectedException` when the exchange refuses the whole action, and `ActionOutcomeUnknownException` when the answer does not have one documented status per order (resting, filled, or the error of a rejected order); rejections of single orders stay in the returned answer, as before. An order dict without a required key raises `InvalidArgumentException` instead of `KeyError`. The return type was documented as a list; it is Hyperliquid's answer, a dict.
- **A price of 0, below 0 or NaN was signed and sent**, as was a NaN size, and a positive price that rounds to 0 at the market's precision (e.g. 0.0000001 for BTC). A missing price (`None`) in `stop_loss()`, `take_profit()`, `modify_order()` or `bulk_order()` reached the SDK, which raised a raw `TypeError`. Every perp order, stop loss, take profit, modify and bulk order now raises `InvalidArgumentException` for a size or price that is not a positive number, or a price that rounds to 0 (or overflows) at the market's precision, before anything is sent. `open_long_position()` / `open_short_position()` check their stop loss and take profit prices the same way before the entry: `True` passed their check as 1, and the stop loss was then refused after the entry had filled. A market order with an unknown symbol is refused before the price is read.
- **`update_stop_loss()` / `update_take_profit()` without an old order could leave part of a position unprotected.** When the new order executed at once, partly (its trigger price was already crossed), or the position grew meanwhile, they returned as if it was protected; the check ran only when there was an old order to cancel. It now runs always, and also checks that the new order is still on the closing side (a position that turned from long to short meanwhile is not protected by a sell stop): `ProtectionReplacementIncompleteException` (with no old order ids) reports the gap. The exception has a new attribute `position`, the position read for the check, when the new order does not cover it.
- **An order id that is not a whole number was cut off**: `cancel_order(10.9, "BTC")` canceled order 10, and `True` order 1. `cancel_order()`, `spot_cancel_order()`, `modify_order()`, `get_open_order_by_id()`, `get_order_status()` and `bulk_cancel()` take an integer (also numpy's, e.g. from a pandas column) or its text and raise `InvalidArgumentException` for anything else, floats included, before sending.
- **`modify_order()` reported a modify with an unknown outcome as a failure** (`ValueError`); it now raises `ActionOutcomeUnknownException`.
- **`cancel_order()` and `spot_cancel_order()` reported some errors as an order that is gone.** For an error that was not the exchange's answer they matched its text ("not found", "already", "no order") and returned `False`, so an HTTP 404 "Not Found" from a proxy read as an order that had filled, while it was still open. They now raise it, as `cancel_order_by_cloid()` does.
- **A cancel whose answer was lost could be reported as not canceled.** It is sent again (cancels are retried), and the exchange then answers that the order is gone, although the first attempt canceled it. In that case the order's status is now read: `True` if it was canceled, `False` if it filled.
- **A rate-limited order kept the key's lock while it waited to retry** (up to 7 seconds with the defaults), so every other order and stop loss replacement of the key waited too. The wait no longer holds it. Cancels and leverage changes did not take that lock at all, so one sent from another thread could cancel the new order in the middle of an `update_stop_loss()` / `update_take_profit()`, which then reported it open; they now wait for a running replacement like orders do.
- **`max_retries` and `retry_delay` were not checked**: with a negative `max_retries` nothing was sent, and an order was reported as having an unknown outcome. Values out of range now raise `InvalidArgumentException` when the client is created.
- **Insufficient margin was recognized only by its exact text**, and an order looked up by its cloid after a lost answer came back with made-up text for every rejection. The margin error is now matched by its start (Hyperliquid may add details), and a looked-up rejection for lack of margin or a post-only crossing (`perpMarginRejected`, `badAloPxRejected`) has Hyperliquid's text: it raises `InsufficientMarginException`, and `maker_order()` reprices after a crossing as usual.
- **`bulk_order()` sent invalid flags**, e.g. `time_in_force="IOC"` or `is_buy="yes"`, and the exchange refused the whole action. A `time_in_force` other than `Gtc`, `Ioc` or `Alo` (also in `create_order()` and `create_spot_order()`) and an `is_buy` or `reduce_only` that is not `True` or `False` now raise `InvalidArgumentException` before anything is sent. `bulk_cancel()` and `add_isolated_margin()` with an unknown symbol raise `UnknownSymbolException` before signing, instead of the SDK's bare `KeyError`.
- **A spot market order could stay on the book.** `create_spot_order()` without `limit_price` sent its marketable price as Gtc; it now defaults to IOC without a price and Gtc with one, as `create_order()`. A size or price that is not a positive number (0, NaN, infinite, or a price that rounds to 0) raises `InvalidArgumentException` before anything is sent.
- **`maker_order()` could fill more than the requested size.** When the status of a canceled attempt could not be read, or did not show it had ended, the chase went on and placed the next order. It now raises `ActionOutcomeUnknownException`. After partial maker fills, the returned order reported only the last part (and its price); it now reports the total filled size and the average price. An unknown symbol or a size below the minimum raised only after the whole timeout; it now raises at once. A size finer than the market's lot step (e.g. 0.001009 BTC) kept the chase going after the tradable part filled; the size is now rounded down to the lot step first. With `fallback="cancel"`, the returned order reported `status="open"` although it was canceled; it is now `"canceled"`. If the chase stops on an error after part of the size filled (e.g. the rest is below Hyperliquid's minimum order value), it raises the new `MakerOrderIncompleteException` with the filled size, average price and the size not filled, the error as `__cause__`; before, the error came alone and a caller could buy the whole size again. An unknown outcome stays `ActionOutcomeUnknownException`; that now includes a chase that stops while an attempt is in the book, e.g. its cancel failed (it may still be there or have filled; it names that order's id and cloid), and one interrupted by an error that is not the library's (e.g. a signal handler's) after an order was sent; before, the error came alone.

Opening and protecting positions:

- **Short positions got no working stop loss or take profit.** `open_short_position()` placed both as sell orders. `stop_loss()` and `take_profit()` now derive the closing side from the position when `is_buy` is omitted (its default is now `None`), and raise `ValueError` if an explicit `is_buy` would not close the position. Calls that already pass the correct `is_buy` behave as before.
- **`open_long_position()` / `open_short_position()` checked the stop loss and take profit prices only after the entry was sent**, so a wrong price left an open, unprotected position. They are now checked before any order is sent, as the prices will be sent (rounded), and must be positive numbers. For a market entry they are checked against the market price; they used to be checked against the entry's slippage limit, which accepted a stop loss above the market for a long (closing it at once) and rejected a valid take profit. A limit entry beyond the mid (a buy above it, a sell below) can fill at once, so its levels are checked against the mid too; a limit entry that rests, against its price. When a market entry fills only partly, the stop loss and take profit are sized to the filled amount.
- **A failed stop loss or take profit after the entry gave no sign that the entry was placed.** `open_long_position()` / `open_short_position()` now raise the new `ProtectionOrderException`: `orders` holds the entry and any order already placed, `leg` names the one that is missing, and the reason is `__cause__`. This includes a limit entry that rests: no stop loss or take profit is placed for a position that does not exist yet.
- **`post_only=True` did not send a post-only order.** It added an undocumented `postOnly` field to a GTC order. It now uses Hyperliquid's `Alo` time in force; the exchange rejects the order if it would match immediately. Applies to perp and spot orders.
- **`add_isolated_margin()` accepted zero and negative amounts.** The exchange treats a negative amount as removing margin. Both now raise `ValueError`.
- **`set_leverage(is_cross=True)` was sent for markets that allow isolated margin only** (most `xyz:` markets); it now raises `ValueError` before sending. Market specs gain `margin_mode`. Exchange errors from `set_leverage()` and `add_isolated_margin()` are raised instead of returned.

Market data:

- **Sizes were rounded with float `round()`, which can round up**, so an order could be larger than requested. They are now rounded down. An unknown symbol raised nothing and was sent with 0 size decimals (1.7 became 2.0); it now raises `UnknownSymbolException` (a `ValueError`).
- **Clients shared metadata across networks and dex lists.** An `extended_universe=True` client created after a default one used specs without the `xyz:` markets, and a testnet client could use mainnet metadata. The cache is now used only by clients for the same network and dex list.
- **A dex whose metadata failed to load was skipped silently**, dropping its markets. Loading now retries and fails as a whole: creating a client fails, and `refresh_market_specs()` raises and keeps the previous specs. A response that is not in the documented format is raised as it is; before, it fell back to another request or to invented values (3 size decimals, 50x leverage).
- **`get_fills_by_time()` returned at most 2000 fills.** It now pages through the range (the exchange keeps only the 10000 most recent fills of an account).
- **Balances of unified accounts were wrong.** In a unified account (the default for accounts created in the Hyperliquid app since February 2026), spot and every perp dex share one balance per token in the spot account, and its USDC already includes the PnL of open positions; the perp account figures are only the part of it backing positions. `get_perp_balance()` returned that part instead of the balance, and `get_all_balances()` would have counted it twice. Both now use the account mode: for unified accounts `get_perp_balance()` returns the spot USDC and `get_all_balances()` the spot balance; standard accounts are unchanged. For portfolio-margin accounts and unknown modes, where no single balance is correct, both raise the new `UnsupportedAccountModeException`. New `get_account_mode()` returns `"standard"`, `"unified"`, `"portfolio_margin"` or `"unknown"`.
- **`get_all_balances()` always raised `AttributeError`**: it called `get_evm_balance()`, which used an SDK method that does not exist. `get_evm_balance()` is removed (HyperEVM balances are not available from the Hyperliquid API); `get_all_balances()` now works, and with `simple=False` also returns `account_mode`.
- **`get_spot_balance()` valued tokens without a perp market at $0** (for example FRAC and PURR). They are now priced from their USDC spot pair.
- **`get_open_orders()` and `get_spot_open_orders()` reported the remaining size as `size`**, so `remaining_size` was wrong for partly filled orders. `size` is now the original size; `filled_size` and `remaining_size` are correct.
- **`Order.order_type` lost its strings**: the time in force (`{"limit": {"tif": "Alo"}}`) and a trigger's `tpsl` (`"sl"`, `"tp"`) came out as `True`, in every order the library returned, placed or open. The model conversion cast to `int`, which also applies to `bool`. `OrderType` is now built explicitly: numbers and numeric strings become `Decimal`, other strings and booleans stay as they are.
- **Open trigger orders were all marked `isMarket: True`**, also Stop Limit and Take Profit Limit orders. It now follows the order type.
- **`maker_order()` retried every rejection as a post-only crossing**, e.g. insufficient margin, until its timeout, and then raised a plain `RuntimeError` without the reason. It now retries only Hyperliquid's post-only rejection ("Post only order would have immediately matched") and raises any other rejection at once.
- **Exchange rejections and missing keys were plain `ValueError` and `RuntimeError`**, with different messages per method (five different ones for a missing key). They are now the library's exceptions, each still the type raised before: an order or modify the exchange refuses raises `OrderRejectedException` with Hyperliquid's text (`InsufficientMarginException` for "Insufficient margin to place order."); a refused leverage change, margin change or transfer raises `ActionRejectedException`; a signed method on a client without a key raises `AuthenticationRequiredException`; invalid arguments raise `InvalidArgumentException`. Stop loss, take profit and spot orders read the exchange's answer with the same code as other orders. An answer in no documented format (also an order status without its documented fields) is `ActionOutcomeUnknownException`, no longer a failure or a raw `KeyError`: for an order the library first looks it up by its client order id; a modify, transfer, leverage or margin change may have gone through. A connect timeout or an HTTP rejection after the retries of an order or transfer is `TimeoutException` / `ClientErrorException`.
- **The `api` functions lacked parameters of the client methods they call**: `buy`/`sell` had no `reduce_only`, `post_only` or `slippage`; `spot_buy`/`spot_sell`, `open_long_position`/`open_short_position`, `close`, `get_order_book`, `get_spot_order_book`, `get_perp_balance` and `get_user_state` lacked some too, and `get_user_state` created a client it never closed. Each now takes every parameter of its method, with the same default; the added ones are keyword-only, after `client`, so positional calls are unchanged. `api.stop_loss`/`api.take_profit` name the price `trigger_price`, as the client does.
- **A market order from `create_order()` could stay in the book.** Without `limit_price` it sent the marketable price as Gtc, so what did not fill at once rested as a limit order; `buy()`/`sell()` and the SDK's `market_open` send IOC. `create_order()` now defaults to IOC without a price and Gtc with one (see Behaviour changes).
- **`cancel_all_orders()` also canceled spot and outcome orders.** The default dex lists them among its open orders. It now cancels every other order, perp orders only (the client's dexes); `spot_cancel_all_orders()` cancels spot orders (see Behaviour changes). An order on a market the client does not know (listed since it was created) is named in `OrdersNotCanceledException`, after the others are canceled; it used to fail the whole cancel inside the SDK.
- **`close_all_positions()` swallowed failed closes.** A position that could not be closed was only logged and left out of the result, which looked like a closed position. Every position is still tried; afterwards the new `ClosePositionsIncompleteException` reports the closed and the failed ones (see Behaviour changes).
- **`modify_order()` reported an executed modify as a failure.** It understood only an order that rests; when the new price matched at once, it raised `ValueError("Failed to modify order")` although the order had filled. It also turned every error into that `ValueError`, e.g. an unknown symbol. The answer is now read like the answer to an order (resting, filled or error, as in `create_order`), and errors keep their type. Placed orders now also have their `type` (`limit`, `stop_loss`, `take_profit`) instead of `unknown`.
- **`close()` reported a partly closed position as closed.** Its order is immediate-or-cancel, and Hyperliquid reports a partly filled one as filled too, with the smaller size; `close()` returned normally (and its warning fired only for orders that never filled). It now raises the new `PositionNotClosedException` with the order and the size still open (see Behaviour changes).
- **A broken key made a silent read-only client.** Any problem with the account (no or malformed key, no address, an `account` that is not a `HyperliquidAccount`) was logged at DEBUG only, and the client went on without a key; the mistake showed at the first order ("requires authentication"). A key missing one character was even accepted, as another key. Creating the client now raises (see Behaviour changes).
- **`refresh_market_specs()` did not make new markets tradeable**: it updated only the library's size table, not the SDK's symbol table orders are placed with, so an order on a market listed after the client was created failed inside the SDK with a `KeyError`. It now loads a new SDK `Info` as at creation and replaces the metadata, the specs and the `Info` of the client and its `Exchange` together.
- **`get_spot_open_orders()` reported every spot order as a plain limit order**: a trigger order (stop loss, take profit) lost its `type`, `trigger_price` and `trigger_condition`, and `reduce_only` was always `False`. Spot and perp orders come in the same `frontendOpenOrders` format and are now read by one parser, so spot orders have every field perp orders have.
- **`get_spot_fills()` and `get_spot_open_orders()` raised `IndexError` on mainnet**: they looked spot tokens up by list position, which no longer matches the token index. Pairs quoted in a token other than USDC are now reported as `BASE/QUOTE` (for example `HYPE/USDT0`) instead of being dropped or mislabeled; USDC pairs still report the token name. Spot methods accept such a full pair name.
- **`proxy=` was not used for the requests a client sends while it is created** (the market metadata): they went out without the proxy. The proxy now applies from the first request.
- **Creating a client requested the market metadata twice**: the default dex's `meta` and the `spotMeta`, which the SDK's `Info` had just fetched while it was created. It now keeps them: two requests fewer per client and per `refresh_market_specs()`.
- **`ClientErrorException` was not exported** from the package, although documented; `from fractrade_hl_simple import ClientErrorException` now works.
- **`HYPERLIQUID_ENV` was documented but never read.** It now selects the network when neither `base_url` nor `env` is passed; the default stays mainnet.
- **Importing the package loaded `.env` into the environment** of the whole process. It no longer does; `.env` is loaded when the library reads its settings from the environment: `HyperliquidAccount.from_env()`, and `HyperliquidClient()` without `account` or without a network (`base_url` or `env`).

- `cancel_order()`, `cancel_order_by_cloid()` and `set_leverage()` with a symbol the client does not know (a typo, `btc`, or a market of a dex the client does not cover) raise `UnknownSymbolException` before anything is signed; the SDK failed with a bare `KeyError` while signing. `cancel_all_orders(symbol)` raises it too: with a misspelled symbol it matched no order and returned as if it had canceled them.
- `cancel_all_orders()` and `spot_cancel_all_orders()` raise the new `OrdersNotCanceledException` (a subclass of `OrderException`, which they raised before) when the exchange does not cancel some orders: `.failed` lists each order still open with its symbol, order id and Hyperliquid's reason, instead of only one combined message.

### New Features

- **Several stop losses and take profits with `open_long_position()` / `open_short_position()`**: `stop_losses=[(price, fraction), ...]` and `take_profits=[...]`, instead of the single `stop_loss_price` / `take_profit_price`. Each level is placed for its fraction of the filled size, rounded down to the lot size, the one of each kind nearest the price taking what rounding left (so a partial fill never loses more at its stops than the full size, before slippage). Prices, fractions (at most 1 together) and the 10 USD minimum of every level are checked before the entry, at the size as it is sent. A level that executes at once (the price had already crossed it) raises `ProtectionOrderException` too, as it protects nothing. `ProtectionOrderException` gains `missing`: the levels not placed, with price and size, and for one whose outcome is unknown `outcome_unknown` and its `cloid`. New `time_in_force=` (with `limit_price`): `"Ioc"` for a market entry with a price limit, its levels checked against the mid.
- **MCP server `fractrade-hl-mcp`, read only by default** (extra `mcp`): lets Claude Code, Codex and Claude Desktop read Hyperliquid accounts and markets, for several configured wallets and any public address, on Hyperliquid's own perps and the HIP-3 dexes you enable (`perp_dexs` in the config, or the `enable_perp_dexs` tool for the session: `xyz:`, `para:`, `io:` ...). 17 tools without trading: accounts, enabling HIP-3 dexes, balances by account mode, positions, open orders, fills, order status, portfolio, funding payments, order status by order id and by cloid, prices, markets, market info, order books, funding rates, and two for risk: `get_position_risk` (an open position's outcomes at its stops and take profits, after fees and estimated slippage, risk/reward, break-even win rate, the size without a stop) and `plan_trade` (the same before entry, and the size from a risk in USD or % of the account); open orders, fills, prices, markets and order books also for spot. Without the trading switch it loads no private key and has no tool that trades; with `--enable-trading` (or `FRACTRADE_MCP_TRADING=1`) it adds 15 trade tools for the accounts with `trading = true`: `buy`, `sell`, `open_position` (a market entry with its stop losses and take profits, the stops required for the whole position), `modify_order`, `cancel_order`, `cancel_order_by_cloid`, `close`, `close_all_positions`, `stop_loss`, `take_profit`, `update_stop_loss`, `update_take_profit`, `cancel_all_orders`, `set_leverage` and `kill_switch`. Each order is checked as it will be signed against the account's limits, per tool: for orders that add risk (closing and protection are exempt) the optional `symbols` allowlist and `max_order_usd`, and the optional risk guardrails: margin per order and in total as a percentage of the account value (`max_margin_pct`, `max_total_margin_pct`), a daily loss stop, an order rate, the market's leverage against `max_leverage`, isolated margin only, and a loss per trade at its stop losses (`max_risk_pct`, for `open_position`; buy and sell that add risk are then refused); `max_slippage` for market orders and closes, `max_leverage` for `set_leverage`; it signs only with API wallets, checked with Hyperliquid's `userRole` before the first signed action and again before every order that adds risk: an account's own key, which could withdraw or transfer, is refused, and tests run every tool through the real signing to check that only trading actions are ever signed; every placed order has a client order id, and one used before for the account is refused; the kill switch halts an account at once and keeps its stop losses; the halt, the account lock, the order rate and the used cloids are shared by every server of one config, as each chat of an assistant may run its own (files with locks in `state` next to the config). `fractrade-hl-mcp --init` creates the config file and an empty key file, for your user only; you create the API wallet in the Hyperliquid app and paste its key into that file, so an assistant can run the rest of the setup without the key ever passing through the chat ([docs/mcp-setup.md](docs/mcp-setup.md)). Setup and reference: [docs/mcp.md](docs/mcp.md), example config: [examples/mcp.example.toml](examples/mcp.example.toml).
- **`base_url` selects the network, as in the Hyperliquid SDK**: `HyperliquidClient(base_url=constants.TESTNET_API_URL)`, with `from hyperliquid.utils import constants`. Only the SDK's constants `MAINNET_API_URL`, `TESTNET_API_URL` and `LOCAL_API_URL` are accepted. Any other URL raises `ValueError`: the SDK would sign for testnet with it, and mainnet would reject every order with "User or API Wallet ... does not exist". Without `base_url`, `HYPERLIQUID_ENV` selects the network, else mainnet.
- **`get_user_funding(start_time, end_time=None, symbol=None)`**: the funding payments of a wallet as `FundingPayment` (time, symbol, market, position size, rate, USDC: positive received, negative paid), every dex, paged (one response holds at most 500). 500 or more payments at one timestamp (a full response) cannot be paged and raise `HyperliquidException` instead of returning a partial list; a range that ends before it starts raises `InvalidArgumentException`. `get_funding_history()` is a market's funding rate history. Also in the `api` module.
- **`get_fill_history(start_time, end_time=None, symbol=None)`**: the fills of a time range as `FillHistory`, with whether Hyperliquid's limits cut it short (`truncated`, `truncated_reason`: it keeps only an account's 10000 most recent fills; a full response of fills in one millisecond cannot be paged). A range that ends before it starts raises `InvalidArgumentException`. `Fill` gains `trade_id`. Also in the `api` module. `get_fill_history`, `get_user_funding`, `get_markets` and `get_account_summary` can be imported from the package like the other `api` functions.
- **`get_account_summary()`**: an account's balances by its account mode, as `AccountSummary` with `CollateralBalance` per token and `DexAccount` per perp dex: account value, USDC available to trade (unified accounts), margin used, positions per dex, and how each figure was computed; figures not established for the mode are `None`. Also in the `api` module.
- **`coin_market(coin)`**: the kind of market of a coin as Hyperliquid names it: `perp` (BTC), `hip3_perp` (xyz:NVDA), `spot` (@107, PURR/USDC), `outcome` (HIP-4: #12, +12, o12) or `unknown`. `Order` and `Fill` gain a `market` field with it, filled in from the coin when not given.
- **`get_order_book(..., decimal=True)`** and `get_spot_order_book(..., decimal=True)`: prices, sizes, spread and mid as `Decimal`, exactly as Hyperliquid sends them (a float can lose digits of large, fine sizes). The default stays float.
- **`perp_dexs=`: trade and read any HIP-3 dex**, not only `xyz`: `HyperliquidClient(perp_dexs=["xyz", "para", "io"])`, the list the SDK's `Info` takes (the default dex is always included). `extended_universe=True` stays the same as `perp_dexs=["xyz"]`; passing both raises `InvalidArgumentException`, and so does a dex the network does not have (the SDK fails with a bare `KeyError`). New `get_perp_dexs()` lists the network's dexes (the SDK's `perp_dexs`), `get_leverage(symbol)` the leverage and margin mode a wallet uses on a market (Hyperliquid's `activeAssetData`), and `get_fee_rates(symbol)` the taker and maker rates a wallet pays on a market (Hyperliquid's `userFees`, on HIP-3 dexes scaled by the market's growth mode and deployer fee scale, as Hyperliquid's fee documentation describes); market specs gain `growth_mode` and `deployer_fee_scale`. `FeeRates` and `Leverage` are exported. `get_price(symbol)`, `get_open_orders(symbol)` and `cancel_all_orders(symbol)` now read only the symbol's dex (as the SDK reads a market order's price), so a market order makes one price request however many dexes the client has; without a symbol they read every dex, as before.
- **`get_user_role(address=None)`**: what an address is on Hyperliquid, as Hyperliquid answers it (the SDK's `user_role`): a user, an API wallet (`agent`, with the account it trades for), a vault, a sub-account, or `missing` (e.g. an API wallet that expired). An order signed with an API wallet's key trades the account the API wallet belongs to.
- **`prepare_order(symbol, size, is_buy, limit_price=None, slippage=None)`**: the size and limit price an order is sent with, without sending it: rounded as the exchange needs them, and without `limit_price` the market price (mid ± slippage). `create_order()` prepares every order with it, so a check of the returned values (e.g. size × price against a limit) is a check of the order that will be signed. Also in the `api` module.
- **Client order ids (`cloid`)**: `create_order()`, `buy()`, `sell()`, `stop_loss()`, `take_profit()`, `create_spot_order()`, `spot_buy()` and `spot_sell()` (and the `api` functions `buy`, `sell`, `stop_loss`, `take_profit`, `spot_buy`, `spot_sell`) take keyword-only `cloid=`, "0x" and 32 hex digits (checked before anything is sent; the SDK checks only the length). Without it an order gets a random one. `Order.cloid` is the client order id of each order the library places and of each open order. An id you choose is known before the order is sent, so an order whose answer was lost can still be found: new `get_order_status_by_cloid()` and `cancel_order_by_cloid()` (the SDK's `query_order_by_cloid` and `cancel_by_cloid`), also in the `api` module. `bulk_order()` sends the `cloid` given in an order's dict. Methods that place several orders (`open_*_position`, `maker_order`, `update_stop_loss`, `update_take_profit`, `close`) give each its own.
- **`get_spot_markets()`**: every spot pair with its current figures (mark, mid and previous-day price, day volume, in the quote token) as `SpotMarket` objects with `Decimal` values, under the symbols the spot methods use (`HYPE`, `HYPE/USDT0`) plus Hyperliquid's own pair name (`@107`). One request. Also in the `api` module.
- **`get_markets()`**: every perp market of the client's dexes with its current figures (mark, mid and oracle price, funding, open interest, 24h volume, margin mode, delisted, at the open interest cap) as `Market` objects with `Decimal` values. Also in the `api` module.
- **Read any wallet without its key.** `HyperliquidClient(trust_env=False)` reads none of this library's settings from the environment, like requests' `Session.trust_env`: no `.env` file, no key, no address, no `HYPERLIQUID_ENV` (HTTP proxy variables are still applied by requests). Without `account` such a client has no key and can never become the `.env` wallet. Every read about one wallet takes the wallet as keyword-only `address=` (default: the client's own account): `get_positions`, `get_open_orders`, `get_spot_open_orders`, `get_open_order_by_id`, `get_order_status`, `get_fills`, `get_fills_by_time`, `get_spot_fills`, `get_stop_loss_price`, `get_take_profit_price`, `get_position_size`, `get_position_direction`, `has_position`, `has_active_orders`, and the matching `api` functions. The balance methods, `get_user_state`, `get_account_mode` and `get_portfolio` already took an address.

- **One documented set of exceptions.** Every exception has a fixed `code` and `retryable` (see the README table). Network and server failures after the retries now raise the library's `NetworkException`, `TimeoutException` and `ServerErrorException` (until now the requests and SDK errors came through as they were); each also is the requests or SDK type it replaces, with the original as `__cause__`. New: `InvalidArgumentException` (a `ValueError`), `UnknownSymbolException`, and `ClientErrorException` for an HTTP 4xx other than the rate limit (also the SDK's `ClientError`). Creating a client now retries its first requests like any other request; the SDK's `Exchange` no longer makes its own startup requests (it signs with the client's market data). Exceptions can be copied and pickled with their message and attributes.

### Behaviour changes to check in your code

- **`Order.order_id` is a number** (`int`), as Hyperliquid sends it and as `Fill.order_id` already was; it was text. Code that compares it with text (`order.order_id == "123"`) must compare with an int. Methods that take an order id still accept text. An `Order` pickled by an earlier version gets its id as a number. `Order` has a new field `cloid` (see New Features).
- **Error messages changed** for exchange rejections (`"BTC order rejected: <Hyperliquid's text>"`, `.reason` holds the text alone) and for a missing key. Types stay compatible: every new exception is also the `ValueError` or `RuntimeError` raised before. Exception: "invalid current price" (a market without a usable price) is now `HyperliquidException`, like `get_spot_price` without a price.
- **`api.stop_loss(stop_price=...)` and `api.take_profit(take_profit_price=...)` are deprecated**: the price is `trigger_price`, as in `HyperliquidClient`. The old keywords still work, with a `DeprecationWarning`; positional calls are unchanged.
- **`create_order()` without `limit_price` sends IOC** (a market order) unless `time_in_force` is passed; before, the default was Gtc. With a price the default stays Gtc.
- **`cancel_all_orders()` leaves spot orders open**: it cancels perp orders only (stop losses and take profits included). Call `spot_cancel_all_orders()` for spot orders.
- **`close_all_positions()` raises `ClosePositionsIncompleteException`** (an `OrderException`, code `CLOSE_POSITIONS_INCOMPLETE`) when a position was not (fully) closed, after trying every position; `closed` holds the orders that went through, `failed` the error per symbol. Before, failures were logged and left out of the returned dict.
- **`close()` raises `PositionNotClosedException`** (an `OrderException`, code `POSITION_NOT_CLOSED`) when the position is still (partly) open afterwards: its order filled only part (`order` holds what was filled and at which price), or the exchange rejected it, e.g. no liquidity within the slippage (`order` is None, `reason` holds Hyperliquid's text, the rejection is `__cause__`); `remaining` is the size still open. Before, it returned the order (and logged a warning if nothing filled).
- **An account that cannot sign raises when the client is created**, as in the SDK: `HyperliquidClient(account=...)` raises `InvalidArgumentException` (a `ValueError`) for a missing or malformed key or address (a private key is 64 hex characters, with or without `0x`); with a `HYPERLIQUID_PRIVATE_KEY` in the environment that cannot be used, `HyperliquidClient()` raises `ConfigurationException`. Without a key in the environment it still reads public data only.
- **A client is not created without its markets**, as in the Hyperliquid SDK: if the market specs cannot be loaded (after the retries), creating the client raises the library's exception, e.g. `NetworkException`. Before, it started with a built-in table of market specs and a warning; that table (`models.MARKET_SPECS`) is removed, as its size decimals could be out of date.
- **No call reloads the markets on its own any more**, as in the Hyperliquid SDK: they are loaded when the client is created. Before, an order call sometimes reloaded them first (when they were older than 24 hours, or for an unknown symbol). An unknown symbol in an order now raises `UnknownSymbolException` at once, without a request. In a long-running program, call `refresh_market_specs()` when markets were listed; it raises on failure (before, it logged a warning and kept the old specs). `cache_market_specs` still lets new clients reuse specs loaded in the last 24 hours.
- Open orders without a trigger (`get_open_orders()`, `get_spot_open_orders()`) now have `trigger_price = None`, like the limit orders the library places. It was `Decimal("0.0")`, the placeholder Hyperliquid sends with `isTrigger: false`; check `order.trigger_price is None` instead of `== 0`.
- Network errors on orders, modifies, transfers and margin changes now raise `OrderOutcomeUnknownException` / `ActionOutcomeUnknownException` instead of being retried. Check the account before acting again; do not resend blindly. Unlike the library's other new exceptions, these two do not inherit the types raised before (requests' errors, the SDK's `ServerError`, `ValueError`), on purpose: a handler that sends again on those would execute the action twice.
- `open_long_position()` / `open_short_position()` raise `ProtectionOrderException` (an `OrderException`, not a `ValueError`) when the entry was placed but a stop loss or take profit was not.
- Cancel methods raise `OrderException` when the exchange does not confirm the cancel.
- `set_leverage()` and `add_isolated_margin()` raise `ValueError` on exchange errors instead of returning the error dict.
- Order sizes are rounded down instead of to the nearest step.
- `stop_loss()` / `take_profit()` raise `ValueError` for an explicit `is_buy` that would not close the position; `open_*_position(stop_loss_price=0)` raises instead of placing no stop loss.
- `cancel_order()` / `spot_cancel_order()` return `False` for an order that already filled, and raise errors they used to turn into `False` by their text (e.g. an HTTP 404).
- `create_spot_order()` without `limit_price` sends IOC unless `time_in_force` is passed; before, the default was Gtc.
- `get_open_orders()` / `get_spot_open_orders()`: `size` is the original order size; use `remaining_size` for what is still open.
- `HYPERLIQUID_ENV=testnet` now selects testnet when neither `base_url` nor `env` is passed.
- `env=` is deprecated and emits a `DeprecationWarning`; pass `base_url=` instead. Passing both raises `ValueError`. `client.env` stays (`"mainnet"`, `"testnet"`, or `None` for `LOCAL_API_URL`).
- `get_perp_balance()` returns the spot USDC for unified accounts, and raises `UnsupportedAccountModeException` for portfolio-margin accounts. Both balance methods make one more request (the account mode). Code that adds `get_perp_balance()` and the spot USDC itself counts a unified account's balance twice; use `get_all_balances()`.
- `get_evm_balance()` is removed, from the client and the package exports.
- `Order` and `Fill` have a new field `market` (see `coin_market`): construction is unchanged, but `dataclasses.asdict()`, equality and the field list include it. `get_open_orders()` and `get_fills()` still return spot and outcome entries too; check `market` to tell them apart. An `Order` or `Fill` pickled by an earlier version gets `market="unknown"`. `Fill` also has a new field `trade_id` (None for an earlier pickle).
- A read about a wallet without an address, on a client without an account, raises the new `AddressRequiredException` with one message everywhere. Before, some reads raised `RuntimeError` and others `ValueError`, with different messages; the new exception is both, so existing handlers still catch it.
- Reads raise `UnknownSymbolException` (a `ValueError`) for an unknown symbol, with the message "Unknown symbol 'X'". `get_order_book()` and `get_funding_history()` raised the SDK's `KeyError` for it; `get_price()` listed every symbol in the message.
- A response body that is not JSON (e.g. an HTML error page) is retried and then raises `ServerErrorException`. Before, reads went on with the SDK's `{"error": "Could not parse JSON: ..."}` dict, and `cancel_all_orders()` raised `OrderException` for it at once.
- `get_portfolio()` raised `ValueError` for every failure, network errors included; they now come as they are, as in every other read (`NetworkException`, `TimeoutException`, ...).
- `get_funding_rates()` no longer wraps its errors in `ValueError("Failed to parse funding rates response: ...")`: an unknown symbol raises `UnknownSymbolException`, a known symbol without a predicted rate `HyperliquidException`.
- `get_order_book()` no longer raises `ValueError` for response formats Hyperliquid does not send.
- `get_open_orders()`, `get_spot_open_orders()` and `get_spot_balance()` no longer skip an entry they cannot parse (with only a log line): it raises. A skipped order made `has_active_orders()` wrong, and a skipped balance made the total too low.
- `get_spot_price()` raises `HyperliquidException` (no longer `ValueError`) when Hyperliquid has no price for the pair.
- Addresses passed to reads are checked before any request (`0x` and 40 hex characters) and raise `ValueError("Invalid address format")`. Before, only `get_user_state()` checked them (and accepted any 42 characters starting with `0x`); the balance methods, `get_account_mode()` and `get_portfolio()` sent any string to the API.
- Code that reads `os.environ` itself right after `import fractrade_hl_simple` no longer sees values from `.env`; call `python-dotenv`'s `load_dotenv()` yourself if you relied on that.

## [0.3.1] - 2026-03-26

### New Features

- **`maker_order()` / `maker_buy()` / `maker_sell()`** — Fee-optimized order execution using post_only orders with automatic chase and fallback. Places maker orders at best bid/ask, re-prices periodically, and falls back to IOC on timeout. Saves ~0.048% per trade (maker rebate vs taker fee).
  - Auto-detects optimal `timeout` and `reprice_interval` from order book spread width
  - Tight spread (<2 bps): 30s timeout, 3s reprice (BTC, ETH, SOL)
  - Medium spread (<20 bps): 45s timeout, 5s reprice (kPEPE, DOGE)
  - Wide spread (>20 bps): 60s timeout, 8s reprice (DYM, low-cap)
  - `fallback` parameter: "ioc" (default), "market", or "cancel"
  - Available as module-level functions via `from fractrade_hl_simple import maker_buy, maker_sell`

- **Order execution metadata** — `Order` dataclass now includes:
  - `is_maker: bool` — whether the order filled as maker or taker/IOC fallback
  - `attempts: int` — number of order placement attempts
  - `elapsed: float` — seconds from first attempt to fill
  - `spread_bps: float` — spread in basis points at time of execution

- **`get_spot_balance()` accepts `prices` parameter** — Pass a pre-fetched price dict to avoid redundant `get_price()` API calls when checking multiple wallets

### Bug Fixes

- **Bug 1: `get_spot_balance` returns $0 for USDC wallets** — USDC, USDT, USDC.e, and USDbC now default to $1 when not found in the perp price dict, since these stablecoins have no perp market
- **Bug 3: Every `HyperliquidClient()` makes unnecessary API calls** — `meta` and `spot_meta` responses are now cached and passed to `Info()` on subsequent instantiations, saving 2 API calls per client init
- **Bug 4: 429 rate limit errors crash instead of retrying** — `_with_retry` now catches SDK `ClientError` with status 429 and retries with exponential backoff, converting to `RateLimitException` after max retries
- **`remaining_size` bug in maker chase loop** — Partial fills during the maker order chase are now tracked correctly via order status API; remaining size decreases appropriately

### Performance

- **`cancel_all_orders()` uses bulk cancel** — Single `bulk_cancel` API call instead of N individual cancels. With 18 open orders, that's 1 API call instead of 18.
- **`cancel_all_spot_orders()` uses bulk cancel** — Same optimization for spot orders.
- **`open_long_position()` / `open_short_position()` reuse entry price** — SL/TP validation uses the entry order's limit price instead of calling `get_price()` again. Saves 1-2 API calls per trade with SL/TP.
- **`maker_order()` no-poll design** — Uses sleep + cancel + single status check pattern (4 API calls/cycle) instead of polling order status every second.

### Data Completeness

New fields added to capture previously dropped API data:

- **`Position.cum_funding`** (`CumFunding` dataclass) — Cumulative funding payments with `all_time`, `since_open`, and `since_change` breakdowns. Essential for true P&L calculation.
- **`Position.max_leverage`** — Maximum allowed leverage for this asset
- **`UserState.cross_maintenance_margin_used`** — Cross-margin maintenance margin usage. Critical for liquidation risk assessment.
- **`Fill.start_position`** — Position size before the fill. Enables reconstructing position history without querying all state changes.
- **`Fill.fee_token`** — Token the fee was paid in (e.g., "USDC")
- **`Order.children`** — Nested child orders for bracket/TP/SL chains
- **`Order.is_position_tpsl`** — Whether the order is a position management TP/SL
- **`Order.trigger_condition`** — Trigger evaluation type: "mark", "index", or "last"
- **Maker order fill price** — `maker_order()` now reports `average_fill_price` when detecting fills via order status API
